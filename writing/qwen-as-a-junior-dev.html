My junior dev runs on a $300 GPU

30 June 2026·6 min read·local AI

I built a Flutter app where the junior developer was a 35-billion-parameter model running on a used graphics card in my room. The senior reviewer was Claude Opus. Here's everything that broke — and the one rule that saved the project.

The setup is simple to describe and surprisingly fiddly to run. A local Qwen3.6-35B-A3B (a mixture-of-experts model, quantised to Q4_K_M) acts as the implementer, driven through a small CLI. Opus 4.8 sits above it as the reviewing gate. The whole thing runs on an RTX 3060 with 12 GB of VRAM — not exactly a datacentre.

The bet behind it: let a cheap, local model do the high-volume grunt work at zero cost per token, and let an expensive frontier model guard the quality. If it works, you get most of the throughput of an AI team for the price of the electricity.

It does work. But only because of one rule I learned the hard way.

Rule #1: green ≠ correct

The single most important thing I can tell you is this:

The worker exits 0, reports "all tests pass," and is lying to you. Run analyze, format, and the tests yourself — every task, no exceptions.

Over and over, the local model finished a task, declared victory, and handed me code with real bugs in it. And the worse part: the harder the task, the more confidently its self-report diverged from reality. Some of what sailed through its own checks:

  • An archive feature that silently blanked an entry's name and colour — data loss, past 16 passing tests.
  • A field quietly aliased to the wrong database column, because a row was typed as dynamic and the wrong access compiled fine.
  • A fire-and-forget database write with no await.
  • setState() called during build().
  • A detail screen that didn't even compile — yet "tests pass," because nothing imported the broken file.

None of these were caught by the model's own test runs. The lesson isn't "the model is bad." It's that a worker's confidence is not evidence. A task is done when I see analyze print No issues found! and the tests go green on my machine. Not before.

Divide labour by novelty, not difficulty

The instinct is to give the cheap model the easy work and reserve the expensive one for the hard parts. That's the wrong axis. What actually predicts success is novelty.

Qwen is excellent at imitation. Point it at a close, recently-built example in the same repo and it produces clean, idiomatic work — it happily reused a test scaffold, mirrored an existing form, extended established wiring. But ask it to invent a mechanism from scratch — the first detail screen, the first filter sheet, the first chart — and it ships broken or half-finished code.

So the division of labour became: Opus implements the first-of-a-kind in each category, and the local model does the imitative extensions, each one pointed at the fresh example to copy. Novelty is the expensive part; repetition is the cheap part. Price your team accordingly.

The real enemy on long tasks: the context cliff

I assumed the failures on big tasks were about capability. They weren't. They were about silent context overflow. The worker didn't gracefully run out of room — it just got cut off mid-thought, and the harness happily reported a "result" built on a truncated half-task. Straight from the server log:

srv send_error: request (128055 tokens) exceeds
the available context size (128000)
slot release: stop processing; srv stop: cancel task

Once I saw that, half the "capability" problems turned out to be length problems. The fixes are unglamorous and effective:

  • Keep each task small — one screen, one feature, one wiring job.
  • Give a priority-ordered read-list so the model spends its budget on the right files.
  • Include a reference skeleton for the one high-risk, current-API piece — the router shape, the provider override, the stream query. That's where a model with few active parameters hallucinates most.
  • Spell out the load-bearing decisions it must not "fix" (amounts as integer minor units; this colour is an int; delete in FK-safe order).

The mental model that stuck: treat the local model like a fast, eager junior who is brilliant at copying, weak at inventing, forgets everything past a certain length, and will cheerfully tell you it's done when it isn't. Manage it like that and it earns its keep.

So… is it worth it?

Yes — with eyes open. A 35B model on a 12 GB card can do real, shippable work, as long as a capable reviewer holds the gate and you never confuse "the worker said it's fine" with "it's fine." The economics are genuinely interesting: the expensive model touches maybe a tenth of the code and catches nearly all of the disasters, while the local one grinds through the volume for free.

I'm building an entire one-person studio on this arrangement, and writing down what I learn as I go. If that's your kind of thing, the rest of the crew is over here.
